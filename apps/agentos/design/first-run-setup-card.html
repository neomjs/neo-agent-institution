This sketch is that card family's Create door: the first-run recipe (neomjs/neo-agent-brain#679) projected inline, inside the operable cockpit, as #12 rules — no wizard wall, no modal, every step dismissible-then-resumable, a visible honest progress line, one quiet confirmation at first persistence. Every row below is the recipe's own output — `evaluate()` on a fake host, run through the CLI on Brain `dbb9d53` (the #732 → #736 stack) — never hand-written status. The card stores nothing: the vessel's main process evaluates, the renderer projects (ADR 0041 §2.3).

What is real here: the budgets are the placement probe's fixture (`probePlacement`, host 32 GiB − 14 GiB other use − a 2.5 GiB VM reservation = 15.5 GiB; guest 16 − 2.5 = 13.5 GiB); the placement reason is the recipe's exact string for that fixture (asserted by `firstRunRecipe.spec`'s placement arm); the preset facts are the `presets` table (`placementPresets.mjs`); every step row is a line of the CLI's `--json` for a cold run on that host. The paths are the host state root's two members (`~/.neo-ai/config`, `~/.neo-ai/secrets`); the record never holds a secret, only those paths.

Why hosted is only "possible" on this machine: it clears the 4 GiB headroom by 13 GiB — its `candidate` status is a missing quality floor (#714's instrument), not a budget. The step says so per row, because "nothing recommended" has more than one cause and the operator chooses with the cause in view. A preset that the probe refuses stays visible and disabled, with the shortfall on the card: the operator learns what the machine would need.

falsifier drills: (1) gray-filter — every status survives hue removal (glyph + word, law-1); (2) no row is green from a receipt: the arm "stale record + failing observers → nothing green" (AC-2) is the card's own unit arm with a fixture IPC; (3) the card holds no secret: DOM + provider state asserted free of the PAT after the credential step (AC-3).

Implementation destination (the ticket's Fix 1, idiom-gated by #24): AgentOS.view.setup.SetupCard, a Neo.container.Panel of the PlaneSetupPanel family — the structural pre-flight decides whether the Connect card becomes this card's second door or a sibling under a shared base; one skin rule either way (the SCSS above is the Connect card's, re-used: the signal left mark, the quiet/primary button pair, the body-role lede). The step list is a Neo.list over a data.Store of step records {id, kind, status, reason, summary, effectId, receipt, observedAt, answer, action}; the run (runId · target · recipeVersion · placement · preset · density) lives on the view root's state.Provider and the card binds to it; the progress line binds to the same Store. No hand-mapped step array, no status in browser storage, no provider field that remembers "completed".

Served cockpit (no vessel): the card shows the CLI's command and projects the CLI's --json when the operator pastes or attaches it — the same renderer over the same JSON, without the IPC. Density (point 7) — the counting definition, not a measurement: a decision is one answered question (the preset; the plane credential; the provider key when the chosen preset requires it; any unfolded advanced binding) or one consent to an effect (three effects); a manual action is a step whose action is an operator instruction rather than a local handler (none on a Docker host where every effect has one). Placement is defaulted, never decided, unless the operator opens the advanced fold. On the 32 GiB path above the design target is therefore 3 + 3 = 6 decisions (hosted is the only possible preset, so its key is asked) and 0 manual actions; on a 64 GiB host with a local preset, 2 + 3 = 5. The measured count of a completed run is the receipt that lands on #351 — this sketch asserts the target, not a run.
