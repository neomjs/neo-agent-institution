## Next: Fleet Manager v1 — an outside operator runs their own institution

Every walkthrough of the cockpit so far had the team as its user: the operator who built the plane, peers who know which button is wired. v1 is the first cut whose bar is someone else — an operator who downloads or forks, follows one supported path, and meets a real institution without maintainer folklore. The gate is behaviour we can observe, **on the installed candidate, end to end**:

> **On a supported first-run profile, an outside operator reaches a real connected institution; every surface reads its state truthfully — cold · live · stale · degraded · unreachable, each with its reason and a next step; the Observatory shows what the team has done and where attention goes, and opens a selected node's source; one representative engineering workflow runs through the cockpit with its context persisted, its review visible and its merge human; and an ordinary supported failure is recovered by following only the product's own guidance.**

[Milestone #1 — FM v1](https://github.com/neomjs/neo-agent-institution/milestone/1) is the tracking milestone; its linked items are the full set. This file names the gate and the load-bearing journeys, never the item list.

**Accounting — three rules.** A merged PR closes an implementation issue and **never retires an installed check**: a row passes when its walkthrough on the installed candidate passes, with a receipt. Every row carries one state — `unknown` (no installed check yet) · `blocked` (a named blocker) · `failed` (checked on a candidate, failed, receipt) · `passed` (candidate/installed version, engine and Brain pins, profile, evidence link) — on one `Row state:` line in its epic's body, written by its steward alone: `row <n> · <steward> · <state> · <date>, candidate Institution <sha> / Brain <sha> / engine <sha> · plan: planned N · done n · added k (gap list accepted <date>) · next: <step> → <holder>`. The state word is the journey check; the counts are diagnostics — `done` never stands in for `passed`, and `added` is read against the operator's tolerance for 30–50 % additions, never as a target. A row's scope changes only with a dated reason in this file — the denominator never improves by silently dropping a failure.

**The first decision — the supported first-run profile.** [D#18965](https://github.com/neomjs/neo/discussions/18965) separates *connect to an existing Brain* from *provision one*, and places the plane, the harness and workspaces, and inference as three separate declarations. The gate needs one declared profile per journey; the Discussion decides it, this file records it. **State: declared (2026-09-30, the operator on D#18965) — v1's supported profile is *provision*, through a setup wizard.** No Agent OS runs in a cloud we operate, so an outside operator has no plane to connect to; the first run sets up their own instance — the shared recipe's cockpit renderer is the wizard, the CLI bootstrap its host-effect half, the curated presets what it offers, and *where the plane runs* its first real question (this machine by default; a cloud deployment the operator provisions is a placement the wizard prepares, never a service of ours). The Brain's [SharedDeployment guide](https://github.com/neomjs/neo-agent-brain/blob/dev/learn/agentos/SharedDeployment.md) is the route's written form until the wizard exists. *Connect* — the packaged vessel attaching to an existing plane with the operator's own GitHub PAT, the path the team's plane already exercises — stays the second door, for a team member whose plane exists. A connecting machine never inherits the server's Docker or GPU requirements by accident; a provisioning machine is told what it needs before anything is written. (The steward's earlier connect-first recommendation carried the falsifier *if no outside operator has a plane to connect to, provision must join the gate* — it fired.)

**The load-bearing path — five journeys.** A row's steward is **one self-selected peer accountable for the row's outcome** — its installed check and its epic's closure. Leaf contributors are named in the same cell with the leaf they claimed and own only that leaf. An unstewarded row is an open option, never a pre-assignment. The done signal is the installed check; the state cell carries its date and receipt.

**Substrate.** The institution's own working rules, graduated in [D#19384](https://github.com/neomjs/neo/discussions/19384), are tracked beside the five rows as one outcome — the `Row state:` line on [neomjs/neo-agent-skills#140](https://github.com/neomjs/neo-agent-skills/issues/140), its owner's. Source merged, package loaded and behaviour validated stay distinct states, and the outcome gates no row.

**How it runs.** Installed checks happen in bounded walkthrough sessions on a named candidate — version, engine and Brain pins, profile — with automated checks wherever they meet the criterion and eyes only where the criterion needs judgment; each session's outcome rewrites the row's `Row state:` line, and the steward broadcasts that line as the subject of a row report — a lifecycle event, like a PR opening. When the report needs a named peer to act, send that peer a direct waking handoff; the broadcast supplies shared awareness. Any peer claims subs; the steward owns the row's outcome and closes its epic. The engine's steady-state cadence is not this line's measure: v1 is the first cut, and its measure is the five rows reaching `passed` on one installed candidate. The cut itself — version, tag, the vessel's packaged build — is recorded when it is prepared; this file names the gate, not the date.

**How the line is re-read.** The rows are walked one at a time; the line is re-read as a whole — the `Row state:` lines, the debt map, the design sweeps and the transport axis together — at every candidate cut, at every change to user obligations, layout or canonical ownership, and otherwise weekly, as the recurring synthesis of [D#19394](https://github.com/neomjs/neo/discussions/19394) (the [first one](https://github.com/neomjs/neo/discussions/19394#discussioncomment-18854592) is the shape). The synthesis has a self-selected holder — for the v1 window, Clio, named on that Discussion — and an independent reader of another family; a peer's acceptance, never presence or an old assignment, establishes the next reader, a holder hands off explicitly, and an unfilled seat names the action that fills it. The read is scheduled only over a reachable team: *sent*, *mailbox-readable*, *route-active* and *delivered* are four different observations, the detect path is [neomjs/neo-agent-brain#503](https://github.com/neomjs/neo-agent-brain/issues/503) and delivery [neomjs/neo-agent-brain#30](https://github.com/neomjs/neo-agent-brain/issues/30), and an unowned transport gap is the first finding, not the backdrop. A finding lands in the owning outcome or debt record with its acceptance tuple — responsibility, holder, next activation, accepted recipient, observed result, remaining obligation — never as a new tracker by default; `Row state:` summarizes and links; a merged repair, an accepted review or an updated row never passes the user outcome by itself — the installed walk does. `Health:` lines, debt lines in PR bodies, `CODEOWNERS` and route wiring stay out of this file until a failed transition names one and its consumer.
